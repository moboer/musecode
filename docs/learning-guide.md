# 基站项目学习文档（初学者版）

> 这份文档写给第一次接触这个项目的人：不假设你懂 WebSocket、不假设你读过方案文档。
> 目标是让你能**跑起来、看懂一次消息的完整旅程、并且敢动手改第一行代码**。
> 操作细节查 `docs/usage.md`，设计原理查方案 v2（在项目仓库外的工作文档里），本文只讲"理解"。

---

## 0. 这个项目在解决什么问题？

设想一个监控大屏页面，上面有 5 个小组件：CPU 曲线、内存曲线、新闻滚动、告警列表、时钟。它们都要从服务器**实时**拿数据。

最直觉的做法是每个组件自己连一条 WebSocket。问题马上来：

- 5 个组件 = 5 条连接、5 次登录校验、5 套重连逻辑，服务器和浏览器都累；
- 组件 A 和组件 B 都关心 CPU 数据，服务器同一条消息要发两遍；
- 某个组件卸载了，它的连接忘了关，就成了泄漏。

**基站的做法**：页面里只留**一个**"总机"（基站客户端），所有组件都跟总机说话：

- 组件说"我想听 CPU 的消息"（订阅），总机记下来；
- 服务器推来一条 CPU 消息，总机按记录分发给关心它的组件；
- 组件想问服务器一个问题（比如"现在的系统信息是什么"），也交给总机代问、代等答复。

好处：一条连接走天下，订阅关系集中管理，组件之间互不知情、互不干扰。服务器端同理有个基站服务（Go 写的），负责保管每个页面的订阅表和消息队列。

**一句话记住：前端基站 = 页面的消息总机；后端基站 = 所有页面的会话与订阅登记处。**

顺带解释两个名词，后面会反复出现：

- **WebSocket（WS）**：浏览器和服务器之间的一条"常开电话线"，双方随时能说话。适合实时推送。
- **长轮询（Long Polling）**：没有电话线时的土办法——浏览器反复问服务器"有我的消息吗？"，服务器有消息才回答、没有就先吊着这通请求。效果类似，成本高些。本项目在 WS 用不了时会自动降级到长轮询，而且**你写的业务代码完全无感**，这是这个项目的核心卖点之一。

## 1. 五个核心概念（先懂这些就够了）

### 1.1 主题（Topic）

消息的"频道名"，用点号分层，例如：

| 主题 | 含义 |
|---|---|
| `metrics.cpu` | CPU 指标事件 |
| `metrics.mem` | 内存指标事件 |
| `news.notice` | 新闻通知事件 |
| `echo` | 回声请求（发什么回什么，演示/联调用） |
| `system.info` | 系统信息请求 |

订阅时可以写通配：`metrics.*` 表示"metrics 下的全部"，`*` 表示全部。

### 1.2 订阅 / 发布（Subscribe / Publish）

- **订阅**：组件登记"我要听这个主题"，之后该主题有消息就自动送到它手上（**推**模式）。
- **发布**：服务器产生一条消息丢给基站，基站只发给订阅了它的页面，没订阅的一条都收不到——这叫"按需订阅"，省流量也省心智。

### 1.3 请求 / 响应（Request / Response）

有些交互是"一问一答"：组件问 `system.info`，基站代问服务器，再把答复递回来。写法和调一个异步函数几乎一样：

```ts
const info = await bs.request("system.info");
```

基站内部给每个问题编了号（消息 id），答复带着同一个编号回来对号入座；问超时没等到答复、或者网络抖动重试，都由基站兜底——而且重试时服务器靠这个编号**不会把同一件事做两遍**（幂等）。

### 1.4 会话（Session）

页面和服务器之间的"长期档案"：你的订阅表、待送达的消息队列、消息序号，都记在这份档案里，档案存在**服务器上**（这是本项目一个关键设计）。

为什么重要？因为这样电话线断了可以换：WS 断了换长轮询，拿着会话 id 回来续上，订阅不用重订、排队中的消息接着发——这就是演示里"强制降级"按钮按下后页面不闪不断的原因。

### 1.5 信封（Message Envelope）

每条消息长一个样，都有固定字段，就像寄信必须写信封：

```json
{
  "type": "event",
  "id": "8f14e45fceea167a5a36dedd4bea2543",
  "ts": 1761532800000,
  "topic": "metrics.cpu",
  "payload": { "value": 42.5, "unit": "percent" },
  "error": null,
  "seq": 108
}
```

- `type`：这条消息的种类（`event` 事件 / `req` 请求 / `res` 答复 / `sub` 订阅动作 / `ping` 心跳……）
- `payload`：真正的内容物
- `error`：**永远存在**，成功时是 `null`，失败时是 `{code, message}`——不用猜"到底有没有出错字段"
- `seq`：服务器给这个会话的消息流水号，客户端靠它发现"中间丢了一条"（丢帧告警）

## 2. 跟着一条消息旅行一遍

以在演示页点一次"echo 请求"为例，看看它都经过谁（括号里是对应的代码文件，强烈建议对着代码读这一节）：

1. **组件**调用 `client.request("echo", { hello: "world" })`（`packages/client/src/client.ts`）
2. 客户端把请求装进信封，交给当前**传输**（`packages/client/src/transports/`）：优先 WS，WS 不可用时是长轮询——业务代码不关心是哪种
3. 请求到达 Go 基站的**Hub**（`server/internal/hub/hub.go` 的 `HandleInbound`），依次过关：
   - 信封格式校验；
   - （开了鉴权时）这个会话的令牌能不能发 `echo`？信封上的 `tenant/sender` 被**盖章覆写**成令牌里的真实身份，不许伪造；
   - 发太快了会被限流拦下；
   - 查注册表：`echo` 的 payload 结构合不合规；
   - 同一个 id 的请求正在执行？直接等那份结果，不重复执行（幂等）
4. **业务处理器**被调用（`server/internal/biz/topics.go` 的 `echo` 函数，一行：原样返回 payload）
5. 答复装进 `res` 信封回到客户端，客户端按 `replyTo` 编号找到正在等的那个 `request()` 调用，把结果递给组件

反方向的事件推送更简单：业务代码调 `hub.Publish("metrics.cpu", ...)`，Hub 查订阅倒排索引（谁订了 `metrics.*`？）→ 放进那些会话的队列 → 各自的传输取走发送。

**读完这一节，你已经理解了这个项目 70% 的行为。** 剩下的都是细节：心跳保活、断线重连、降级切换、队列满了丢帧计数等等，都是围绕这条主线打转。

## 3. 代码地图（从哪开始读）

按推荐顺序读，前 3 个文件读完就能跟人讲清这个项目：

| 顺序 | 文件 | 看点 |
|---|---|---|
| 1 | `packages/protocol/src/index.ts` | 信封长什么样、错误码、主题匹配规则（前后端共用同一份定义） |
| 2 | `server/internal/hub/hub.go` | 服务端的心脏：消息进来后的全部处理流程 |
| 3 | `packages/client/src/client.ts` | 客户端的心脏：连接状态机、订阅管理、重连与降级 |
| 4 | `server/internal/hub/session.go` | 会话档案里到底存了什么 |
| 5 | `packages/client/src/transports/` | 两种传输（WS / 长轮询）如何"只是读写端" |
| 6 | `server/internal/biz/topics.go` | 示例业务：5 个请求处理器 + 2 个定时发布器，全项目最易读的业务代码 |
| 7 | `server/internal/auth/` + `internal/registry/` | 鉴权五道关与注册表校验，想深入安全时再看 |
| 8 | `packages/client/src/hosts/` | SharedWorker 多标签单连接的实现，想深入进阶时再看 |

目录速记：

- `packages/protocol/` 协议（两端共享的"普通话"）
- `packages/client/` 前端核心 SDK（框架无关）
- `packages/component|react|vue/` 三种用法外壳（机制不在这，在 client 里）
- `server/` Go 后端（`internal/hub` 是核心，`internal/transport/httpx` 是两个门面）
- `registry/topics.json` 主题注册表（主题契约的唯一出处）
- `examples/web/` 演示页，5 个组件共享一条连接

## 4. 跑起来（10 分钟）

环境：Go 1.24+、Node 20.19+。

```bash
npm install
npm run dev
```

打开 http://localhost:5173 ：

- 看到 5 个面板都在动（指标数值在跳、新闻在滚动）= 成功；
- 点面板上的"强制降级"：连接从 WS 切到长轮询，数据不断流——这就是会话续接在工作；
- 浏览器控制台或服务端日志里能看到连接/会话的日志。

另开一个终端验证服务端活着：`curl http://localhost:8080/api/health`，会返回会话数、丢帧总数、鉴权模式等。

跑测试（改代码前先让它们全绿，心里有底）：

```bash
npm test    # 前端 39 个用例 + Go 全部用例
```

## 5. 动手练习（由浅入深）

每题都给了验收标准，做完一题再下一题。

### 练习 1：订一个新主题看数据（改 3 行）

在演示页任意组件里订阅 `news.notice`，把收到的新闻标题打到控制台。

- 提示：找 `examples/web/src/` 里现有的 `subscribe("metrics.cpu", ...)` 照着写；订阅写法在 `docs/usage.md` §3。
- **验收**：控制台每 5 秒出现一条新闻标题。

### 练习 2：给 echo 之旅装个行车记录仪

用客户端的旁路观测 API 把进出帧都打出来，发一次 echo 请求，对照第 2 节的旅程数一数帧。

- 提示：`client.onTraffic((msg, dir) => ...)`，只观测不产生订阅。
- **验收**：能说出一次请求往返共几帧、每帧的 `type` 分别是什么、答复靠哪个字段对上号。

### 练习 3：新增一个主题（全链路）

加一个 `time.now` 请求主题：问它，它回当前服务器时间。

1. `registry/topics.json` 加一条（方向 `request`，payload 为空对象）；
2. `npm run gen:topics` 重新生成双端代码（**不要手改生成文件**）；
3. `server/internal/biz/topics.go` 里照着 `systemInfo` 写一个处理器并注册；
4. 前端 `await bs.request("time.now")` 验证。

- **验收**：拿到时间戳；故意把请求 payload 发成数组 `[]`，会收到 `BAD_MESSAGE`——恭喜你撞上了注册表校验，它在保护你的处理器。

### 练习 4：打开鉴权，亲手被拒一次

```bash
# 停掉 dev，改用 jwt 模式启动服务
go -C server run ./cmd/basestation -auth-mode jwt -auth-secret dev-secret -dev-token
# 换一张"小权限"令牌：只能看 metrics
curl -X POST localhost:8080/api/auth/dev-token \
  -d '{"sub":"guest","subscribe":["metrics.*"],"publish":[],"ttlSeconds":300}'
```

拿这张令牌连上后，试着订阅 `news.notice` 或发一个 `echo` 请求。

- **验收**：订阅收到 `FORBIDDEN` 的 error 帧、请求被 `FORBIDDEN` 拒绝；服务端日志里出现 `audit:` 开头的记录。再试试不带令牌连接——直接 401。体会一下"前端验过不算数，后端每道关都复核"是什么意思。

### 练习 5：多标签只用一个连接（进阶）

用 `createBestClient({ url, workerUrl })` 写一个小页面（用法见 `docs/usage.md` §12.5），同浏览器开 3 个标签页都订阅 `metrics.cpu`，然后看 `curl localhost:8080/api/health` 的 `sessions` 数。

- **验收**：3 个标签页都收到数据，而服务端会话数只增加 1；关掉一个标签页，其余照常；全关后再开，恢复正常。

## 6. 排障速查

| 现象 | 先查什么 |
|---|---|
| 演示页打不开 / 一片空白 | `npm run dev` 两个服务都起来了吗？5173 和 8080 端口是否被占用 |
| 页面连不上基站 | `curl localhost:8080/api/health`；再看服务端日志的报错 |
| 一直 401 | 服务端开了 jwt 模式但客户端没带令牌，或令牌过期——重新换一张 |
| 订阅了却收不到消息 | 主题名拼写对吗？服务端真的在发布这个主题吗（看 `system.info` 返回的主题列表）？鉴权模式下你的令牌 `sub_acl` 包含它吗？ |
| 请求报 `BAD_MESSAGE` | payload 不符合注册表里该主题的 schema，去 `registry/topics.json` 对照字段与类型 |
| 请求报 `RATE_LIMITED` | 发太快触发限流，令牌的 `rate` 或服务端 `-rate-per-sec` 是上限 |
| 改了主题不生效 | 忘了跑 `npm run gen:topics`，或者改的是生成文件（会被覆盖） |
| 测试红了 | 先看是 TS 还是 Go 红；`npm run test:server` 单独跑 Go；改动前先确认基线全绿再对比 |

## 7. 术语表（一句话版）

| 术语 | 一句话 |
|---|---|
| 基站（BaseStation） | 消息总机：前端一个实例管全页消息，后端一个服务管全部会话 |
| 主题（Topic） | 消息的频道名，点号分层，可通配订阅 |
| 订阅（Subscribe） | 登记"我要听这个频道"，之后自动收到推送 |
| 信封（Envelope） | 所有消息的统一格式：type/id/ts/payload/error 恒定存在 |
| 会话（Session） | 存在服务端的长期档案：订阅表、队列、序号；换传输靠它续接 |
| 传输（Transport） | 真正搬运字节的通道：WebSocket 或长轮询，可互换 |
| 降级（Degrade） | WS 不可用时自动改走长轮询，业务无感 |
| 心跳（Heartbeat） | 定期发的"我还在"信号，双方靠它发现假死连接 |
| 幂等（Idempotent） | 同一请求重复到达只执行一次，靠消息 id 去重 |
| seq / 缺口 | 会话内消息流水号；跳号 = 中间丢帧，客户端会告警 |
| 令牌（Token） | JWT 格式的通行证，写明你是谁、能订什么、能发什么、发多快 |
| ACL | 访问控制清单：令牌里"能订/能发"的主题范围 |
| 盖章（Stamp） | 服务端按令牌覆写信封的 tenant/sender，前端伪造无效 |
| 注册表（Registry） | 主题契约的唯一出处，前后端代码都由它生成 |
| SharedWorker | 多个标签页共享的一个后台线程；基站跑在里面就实现了多标签单连接 |
| 宿主（Host） | core 运行的环境（主线程 / Worker），环境依赖都经宿主接口注入 |

## 8. 学完这份文档之后

1. 通读 `docs/usage.md`（全部 API 的操作手册）；
2. 对着第 2 节的旅程，把 `hub.go` 的 `HandleInbound` 从头到尾读一遍，你会发现每一关都对得上；
3. 挑练习 3 的主题，试着给它加上鉴权要求（只让某种令牌能发），你就摸到这个项目最核心的设计主张了：**前端只是镜像，服务端才是执法者**。
